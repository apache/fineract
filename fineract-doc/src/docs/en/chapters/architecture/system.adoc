= System Overview 

image::platform-systemview.png[Platform System Overview,title="Platform System Overview"]

Apache Fineract is the core engine of a financial institution's information
system. It can be used by non-banks or banks. 

It holds the clients, accounts, products, transactions and ledger, and
it exposes every one of those capabilities through a single HTTPS REST API.
Nothing in the platform is reachable by any other route: there is no alternate
back door for a favoured channel, and no private interface reserved for a
bundled front end. 

Fineract is a headless application. 

== Channels and applications

Financial institutions reach their customers through many channels at once, and
the mix differs by institution and by market. A customer may walk into a branch
and transact with a teller; organise into a group or centre that meets a field
officer at an agreed time and place; use a self-service portal or mobile
application; transact over an ATM, point-of-sale or card network the institution
participates in; use a mobile money or wallet service; or deal with a third-party
agent who sells the institution's products alongside others.


Each of these is served by a third party application, and those applications are the
diagram's top band. The grouping shown is illustrative rather than prescriptive.


== The API gateway

In a production deployment, clients apps do not address Fineract instances directly.
They address an API gateway or edge layer that sits in front of the platform and
carries the concerns that belong at the perimeter:

* TLS termination with managed, automatically rotating certificates — Fineract
  enforces HTTPS and ships a self-signed certificate for localhost development
  only;
* authentication and token issuance, and coarse authorisation, ahead of the
  platform's own fine-grained permission checks;
* rate limiting, throttling and request size limits;
* routing of requests to the appropriate instance type (see below);
* a single point for edge audit logging, tracing and observability.

See the *Security* chapter for the authentication schemes the platform supports
and for deployment guidance on the proxy layer.

== Instance types and scaling

A Fineract deployment is not a single process. Because reads and writes are
separated in the architecture, the same binary can be started in three instance
types, enabled independently by configuration:

[cols="1,3"]
|===
| Write instances
| Serve the state-changing APIs. Commands pass through the command pipeline,
  which gives audit, maker-checker and idempotency. Business events are raised
  here, and database schema migration runs only on these instances.

| Read instances
| Serve the query APIs, and may be scaled out horizontally against read
  replicas, using read-only database connections. This is the usual way to take
  query load off the primary.

| Batch instances
| Run the scheduled and Close of Business work, including partitioned jobs
  distributed across manager and worker nodes.
|===

In a single-instance deployment all three are enabled together, which is the
default and requires no configuration. A common scaled topology is one write
instance, one or more batch instances, and several read instances backed by read
replicas. The *Deployment* chapter covers the configuration in detail.

== State and integration fabric

Beneath the instances sit the tenant databases. Fineract is multi-tenant by
design, isolating each institution's data in its own database or schema, which
makes it equally suitable for a single local installation and for a
Software-as-a-Service offering.

Alongside the databases, the reliable event framework publishes business events
to a downstream message channel in a standardised Avro format, with ordering and
at-least-once delivery guarantees. Events are the second integration surface
after the API, and they are what allow surrounding systems to react to what
happens in the core without polling it.


== Surrounding systems

A core banking platform (or loan management system with core ledger) is never deployed alone. 
Around Fineract an institution typically operates a set of specialised systems, and the lower band of the
diagram names the categories most often seen:

* a payment hub or payment switch, connecting the institution to domestic
  instant payment schemes, card networks and mobile money operators;
* loan origination and credit decisioning, where applications are captured,
  underwritten and approved before an account is opened in the core;
* credit risk and scoring services, including alternative-data scoring models;
* fraud monitoring and AML, sanctions and transaction screening;
* identity, KYC and credit bureau services;
* reporting, business intelligence and analytics, usually reading from a data
  warehouse fed from the replicas or the event stream rather than querying the
  transactional database;
* core accounting, ERP and treasury systems, which exchange general ledger
  postings with the platform;
* notification and messaging services.

None of these other components or systems are part of the Apache Fineract core distribution. 
They are separate products or projects, commercial or open source, and an institution may combine
several of them, split one across vendors, or operate without some of them
entirely. They are drawn here because the shape of a real deployment is not
legible without them — and because the way they attach matters. Each integrates
through the API gateway, through the event stream, or both. None of them reaches
into the platform's database, and none of them is a privileged component.

For capabilities that belong inside a transaction rather than beside it, the
platform offers extension points instead of integration: custom modules and
plugin JARs, configurable business steps within jobs such as Close of Business,
hooks, and custom command handlers. The *Custom Modules* chapter describes these.

== What this means for an implementer


. *The API is the contract.* It is described by an OpenAPI descriptor from which
  client SDKs are generated, and backward compatibility is enforced
  automatically on every change. Build against it with confidence.
. *The core stays core.* Resist the temptation to add additional origination workflow,
  scoring models, channel-specific logic or reporting pipelines inside the
  platform. They belong in the surrounding systems, where they can evolve on
  their own release cycle.
. *Scale the parts that need it.* Query load, write load and batch load have
  different profiles. Separating the instance types is usually a cheaper answer.
