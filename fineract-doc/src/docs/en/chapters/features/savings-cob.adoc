= Savings COB (Close of Business)

== Overview

The Savings Close of Business (COB) feature is a Spring Batch–based, partitioned pipeline that executes daily end-of-day processing on every non-closed savings account. It mirrors the manager/worker architecture used by Loan COB but operates on `SavingsAccount` aggregates: a manager node partitions the account population by id ranges, dispatches partitions through a message channel, and one or more worker nodes pull partitions, lock the accounts, run an ordered list of business steps against each account, persist the result, and release the lock.

=== Purpose

A modern core banking platform needs a deterministic, fault-tolerant, horizontally scalable mechanism to advance the state of every savings account once per business day — posting interest, applying scheduled charges, marking dormancy, and so on. The legacy `POST_INTEREST_FOR_SAVINGS` job processed accounts sequentially in a single tasklet without distributed locking, fault tolerance, or extensibility. Savings COB replaces that with the same partitioned framework already used by Loan COB so that:

* the work can be split into partitions processed by one or more worker nodes,
* each account is processed in its own transaction,
* per-account failures are isolated (skipped and recorded on the lock) rather than aborting the batch,
* the list of operations performed at COB is configurable per tenant through `m_batch_business_steps`.

=== Scope

The scope of this document includes:

* The `SAVINGS_COB` Spring Batch job and its manager/worker step topology
* The `SavingsCOBBusinessStep` extension point and the six bundled steps (`POST_INTEREST_FOR_SAVINGS`, `PAY_DUE_SAVINGS_CHARGES`, `APPLY_ANNUAL_FEE_FOR_SAVINGS`, `UPDATE_SAVINGS_DORMANT_STATUS`, `UPDATE_DEPOSITS_ACCOUNT_MATURITY_DETAILS`, `ADD_ACCRUAL_TRANSACTIONS_FOR_SAVINGS`)
* Distributed locking via `m_savings_account_locks` and the savings values of the shared `LockOwner` enum
* The inline Savings COB (`POST /jobs/SAVINGS_COB/inline`)
* The business step configuration API for the savings job (`/jobs/SAVINGS_CLOSE_OF_BUSINESS/steps`)
* The `last_closed_business_date` tracking column on `m_savings_account`
* Partitioning, catch-up mode, retry/skip semantics, and the stayed-locked business event
* Tenant-level configuration through `application.properties`
* Upgrade and coexistence with the legacy standalone savings jobs

=== Applicability

* All savings accounts in a non-closed status: `SUBMITTED_AND_PENDING_APPROVAL`, `APPROVED`, `ACTIVE`, `TRANSFER_IN_PROGRESS`, `TRANSFER_ON_HOLD`.
* Tenants that have at least one row in `m_batch_business_steps` with `job_name = 'SAVINGS_CLOSE_OF_BUSINESS'`. If no business steps are configured, the partitioner stops the job execution.

=== Definitions and Key Concepts

*COB business date:* The business date being closed by this run, obtained via `BusinessDateType.COB_DATE` from the tenant's `ThreadLocalContextUtil`. Stored in the job's execution context as `BusinessDate`.

*Catch-up mode:* When `IS_CATCH_UP=true`, the partitioner and reader only consider accounts whose `last_closed_business_date` equals the target date (i.e. accounts already partially processed for that date), as opposed to advancing accounts that have never been processed.

*Partition:* A contiguous range of savings account ids (`minId`–`maxId`) of size `partition-size`. Each partition is dispatched as a separate worker step via the `outboundRequests` channel and pulled by a worker through `inboundRequests`.

*Business step:* A `SavingsCOBBusinessStep` bean executed inside the worker's item processor. The ordered list of steps per tenant is stored in `m_batch_business_steps` and resolved by `COBBusinessStepService.getCOBBusinessSteps(SavingsCOBBusinessStep.class, "SAVINGS_CLOSE_OF_BUSINESS")`.

*Lock owner:* The role under which a lock row in `m_savings_account_locks` was placed — a value of the shared `org.apache.fineract.cob.domain.LockOwner` enum: `SAVINGS_COB_CHUNK_PROCESSING` for batch processing or `SAVINGS_INLINE_COB_PROCESSING` for the inline catch-up job (`INLINE_SAVINGS_COB`).

*Stayed-locked account:* An account whose lock row was not removed by the end of the run because chunk processing failed for it. Surfaced via the `SavingsAccountsStayedLockedBusinessEvent` event.

== Design Decisions and Considerations

=== Reusing the COB framework instead of forking

The job reuses `COBBusinessStepService`, `CustomJobParameterResolver`, `InitialisationTasklet`, `ResetContextTasklet`, `CobWorkerStepListener`, `ApplyCommonLockTasklet`, `COBStepExecutionSplitter`, `RemotePartitioningManagerStepBuilderFactory`, and `RemotePartitioningWorkerStepBuilderFactory` from `fineract-cob`. Only the savings-specific pieces (partitioner, reader/processor/writer, business step interface, id queries) are new. This keeps the operational behavior — partition size, poll interval, chunk size, retry/skip — identical to Loan COB and configurable through the same `fineract.partitioned-job.partitioned-job-properties[*]` keys.

The lock model is shared with Loan and Working Capital Loan COB rather than duplicated:

[cols="2,3",options="header"]
|===
| Savings class | Generic contract it builds on
| `SavingsAccountLock` (`fineract-savings`) | Extends the `AccountLock` mapped superclass (`fineract-cob`). An `@AttributeOverride` maps the inherited `loanId` property to the `savings_id` column, so `loanId` holds the savings account id.
| `SavingsAccountLockRepository` | Implements the generic `AccountLockRepository<SavingsAccountLock>` and supplies its own `deleteOrphanedLocksForProcessedAccounts` JPQL query against `SavingsAccount`.
| `SavingsAccountLockServiceImpl` | Extends `AbstractAccountLockService<SavingsAccountLock>` and overrides `getCobLockOwners()` to return `SAVINGS_COB_CHUNK_PROCESSING` and `SAVINGS_INLINE_COB_PROCESSING` instead of the loan owners.
| `UnlockProcessedSavingsTasklet` | Extends the generic `UnlockProcessedAccountsTasklet<SavingsAccountLock>`.
| `InlineSavingsCOBExecutorServiceImpl` | Extends `InlineCommonLockableCOBExecutorService<SavingsAccountLock>`, the same base class as the loan inline COB.
|===

Lock owners are values of the shared `LockOwner` enum (`SAVINGS_COB_CHUNK_PROCESSING`, `SAVINGS_INLINE_COB_PROCESSING`); there is no savings-specific lock owner enum.

=== Per-account lock with version column

`m_savings_account_locks` uses `savings_id` as the primary key plus an optimistic-lock `version` column. The lock is inserted by `ApplySavingsLockTasklet` *before* chunk processing starts and is removed by `AbstractSavingsItemWriter` after the account is successfully saved. This prevents two workers (or worker + inline COB) from updating the same savings account concurrently, and lets per-chunk listeners record errors against the lock row without losing the lock.

=== Skip-and-record over fail-fast

The worker step is `faultTolerant()` with an immediate retry policy on `Exception` bounded by `retry-limit` (`StepRetryPolicyFactory.immediateRetryPolicy(...)`), `skip(Exception.class)` and a skip limit taken from `PropertyService#getSkipLimit` (the configured `skip-limit`, or `chunk-size + 1` when it is left empty). A failure on a single account is caught by `ChunkProcessingSavingsItemListener`, which writes the error message and serialized stacktrace to that account's lock row in a new transaction and lets the rest of the chunk continue. The lock is intentionally *not* released on failure — the row remains so an operator can investigate, and the `StayedLockedSavingsTasklet` at the end of the job publishes a `SavingsAccountsStayedLockedBusinessEvent` listing those accounts.

=== Account-agnostic item listener shared with Loan COB

The read/process/write error handling is identical between Loan COB and Savings COB, so it lives once in the abstract base `AbstractItemListener<S extends AbstractPersistableCustom<Long>>` (`fineract-cob/src/main/java/org/apache/fineract/cob/listener/AbstractItemListener.java`). It implements the `@OnReadError`, `@OnProcessError` and `@OnWriteError` callbacks and, for each failed account id, calls `LockingService.updateLockError(...)` inside a `REQUIRES_NEW` transaction. Concrete listeners supply only what differs:

[cols="2,3"]
|===
|*Hook* |*Purpose*

|`getLockOwner()`
|The `LockOwner` that scopes the lock-row updates — `SAVINGS_COB_CHUNK_PROCESSING` for `ChunkProcessingSavingsItemListener`, `SAVINGS_INLINE_COB_PROCESSING` for `InlineCOBSavingsItemListener`, `LOAN_COB_CHUNK_PROCESSING` / `LOAN_INLINE_COB_PROCESSING` for the loan listeners.

|`getAccountTypeLabel()`
|The human-readable noun used to build the lock-error message. Defaults to the generic `"Account"`; both savings listeners override it to `"Savings"` and the loan listeners to `"Loan"`, so messages read `"Savings (id: %d) processing is failed"` and `"Loan (id: %d) reading is failed"` respectively.
|===

[NOTE]
====
The label is intentionally a per-subclass override rather than a hardcoded string in the base class: it keeps each domain's diagnostic message stable (and its tests green) while the shared error-recording logic stays in one place. Adding a new account type to COB means subclassing `AbstractItemListener` and overriding these two hooks — no error-handling code is duplicated.
====

=== Garbage-collecting orphaned locks

A lock row can outlive the processing it guarded: `m_savings_account_locks` may still hold a row whose `error` is `null` even though the account's `last_closed_business_date` was already advanced to the lock's COB business date. `UnlockProcessedSavingsTasklet`, the last step of the job, extends the generic `UnlockProcessedAccountsTasklet` and calls `AccountLockService.removeOrphanedLocksForProcessedAccounts()`. In `SavingsAccountLockServiceImpl` this delegates to `SavingsAccountLockRepository.deleteOrphanedLocksForProcessedAccounts(getCobLockOwners())`, a JPQL delete that removes every lock row that:

* is owned by `SAVINGS_COB_CHUNK_PROCESSING` or `SAVINGS_INLINE_COB_PROCESSING` (both savings owners are considered),
* has no `error`,
* has a non-null `lock_placed_on_cob_business_date`, and
* belongs to a savings account whose `last_closed_business_date` equals that `lock_placed_on_cob_business_date` — proof that all business steps completed for that date.

Locks carrying an error are never removed by this step.

== Database Design

=== Overview

Savings COB adds one new table (`m_savings_account_locks`) and one new column on the existing `m_savings_account` table for date tracking, plus rows in the standard `job` and `m_batch_business_steps` tables.

=== Existing Tables

*m_savings_account*: Read by `RetrieveSavingsIdServiceImpl` for partitioning and chunk loading, then updated by the writer to advance `last_closed_business_date`.

*m_batch_business_steps*: Holds the per-tenant ordered list of `SavingsCOBBusinessStep` step names under `job_name = 'SAVINGS_CLOSE_OF_BUSINESS'`.

*job*: Standard scheduled-job table — a `Savings COB` row is inserted so the scheduler can trigger the batch job.

*m_external_event_configuration*: Receives an entry for `SavingsAccountsStayedLockedBusinessEvent` so the event can be externalized.

=== Table: m_savings_account_locks

The `m_savings_account_locks` table stores one row per savings account that is currently held by a COB run. Created by changelog `2006_add_savings_account_locks.xml`. It is mapped by the `SavingsAccountLock` entity, which inherits all columns from the generic `AccountLock` mapped superclass and only remaps the id column to `savings_id`.

[cols="1,2,1,3",options="header"]
|===
| Column Name | Type | Constraints | Description
| savings_id | BIGINT | PK, FK to `m_savings_account.id`, not null | The locked savings account
| lock_owner | VARCHAR(100) | not null | Value of the shared `LockOwner` enum: `SAVINGS_COB_CHUNK_PROCESSING` or `SAVINGS_INLINE_COB_PROCESSING`
| lock_placed_on_cob_business_date | DATE |  | The COB business date the lock belongs to; used by stayed-locked and orphaned-lock cleanup queries
| error | VARCHAR(255) |  | Per-account failure message; populated by `ChunkProcessingSavingsItemListener` / `InlineCOBSavingsItemListener` when a chunk item fails, or by the inline COB executor when an inline attempt fails
| stacktrace | TEXT |  | Serialized throwable that produced `error`
| version | BIGINT | not null | JPA `@Version` optimistic-lock counter, incremented by `upgradeLock`
| lock_placed_on | DATETIME / TIMESTAMP WITH TIME ZONE | not null | Audit timestamp when the lock was placed (DB-specific column type)
|===

=== Changes to Existing Tables

==== m_savings_account

The `last_closed_business_date` column is added by changelog `2004_add_savings_account_cob_infrastructure.xml`. An index `FK_savings_account_last_closed_business_date` is added on the same column to keep the partitioner query selective on large account populations.

[cols="1,2,1,3",options="header"]
|===
| Column Name | Type | Constraints | Description
| last_closed_business_date | DATE |  | The most recent COB business date for which all configured business steps completed for this account. Set by `AbstractSavingsItemProcessor.setLastRun(...)` after the business-step chain returns.
|===

== Configuration

=== Job properties

The job is registered as a partitioned job in `application.properties` and inherits all standard partitioned-job knobs. The defaults below can be overridden via environment variables.

[source,properties]
----
fineract.partitioned-job.partitioned-job-properties[2].job-name=SAVINGS_COB
fineract.partitioned-job.partitioned-job-properties[2].chunk-size=${SAVINGS_COB_CHUNK_SIZE:100}
fineract.partitioned-job.partitioned-job-properties[2].partition-size=${SAVINGS_COB_PARTITION_SIZE:100}
fineract.partitioned-job.partitioned-job-properties[2].retry-limit=${SAVINGS_COB_RETRY_LIMIT:5}
fineract.partitioned-job.partitioned-job-properties[2].skip-limit=${SAVINGS_COB_SKIP_LIMIT:}
fineract.partitioned-job.partitioned-job-properties[2].poll-interval=${SAVINGS_COB_POLL_INTERVAL:500}
----

The `job-name` must match `SavingsCOBConstant.JOB_NAME` (`SAVINGS_COB`). The `skip-limit` default is deliberately empty: an empty value binds to `null`, and `PropertyService#getSkipLimit` then falls back to `chunk-size + 1`. Setting a number pins the skip limit independently of `chunk-size`.

[IMPORTANT]
====
Savings COB has no thread pool settings. The worker step deliberately registers no task executor, exactly like Loan COB (see the comments in `LoanCOBWorkerConfiguration#loanCOBWorkerStep` and `SavingsCOBWorkerConfiguration#savingsCOBWorkerStep`): with a task executor, Spring Batch 6 processes the items of a chunk concurrently outside the chunk transaction, so business-step writes would commit independently of the chunk write (FINERACT-2621). Without an executor, item processing stays on the step thread and joins the chunk transaction.

Concurrency comes from partitioning instead: lower `partition-size` to produce more partitions and add worker instances to process them in parallel.
====

[#savings-cob-business-step-configuration]
=== Business step configuration

The ordered list of steps executed per account is read from `m_batch_business_steps` filtered by `job_name = 'SAVINGS_CLOSE_OF_BUSINESS'` and ordered by `step_order`. A step is only resolvable if its `step_name` matches a `SavingsCOBBusinessStep` bean's `getEnumStyledName()`.

By default the seed migration installs six steps in this order: `POST_INTEREST_FOR_SAVINGS` (1), `PAY_DUE_SAVINGS_CHARGES` (2), `APPLY_ANNUAL_FEE_FOR_SAVINGS` (3), `UPDATE_SAVINGS_DORMANT_STATUS` (4), `UPDATE_DEPOSITS_ACCOUNT_MATURITY_DETAILS` (5) and `ADD_ACCRUAL_TRANSACTIONS_FOR_SAVINGS` (6).

Operators change the list per tenant through the business step configuration API, the same one Loan COB uses (`ConfigureBusinessStepApiResource`). `SavingsBusinessStepCategoryServiceImpl` registers the `SAVINGS` category and ties it to the `SAVINGS_CLOSE_OF_BUSINESS` job name and the `SavingsCOBBusinessStep` interface, which is what makes the savings job configurable there:

[cols="2,3",options="header"]
|===
| Endpoint | Behaviour
| `GET /v1/jobs/SAVINGS_CLOSE_OF_BUSINESS/steps` | Returns the configured steps with their order.
| `PUT /v1/jobs/SAVINGS_CLOSE_OF_BUSINESS/steps` | Replaces the whole configured list with the `businessSteps` array of the request body and answers `204 No Content`.
| `GET /v1/jobs/savings/available-steps` | Returns every `SavingsCOBBusinessStep` bean that can be configured. The path segment is the category name (case-insensitive) or the job name `SAVINGS_CLOSE_OF_BUSINESS`.
|===

[source,json]
----
PUT /v1/jobs/SAVINGS_CLOSE_OF_BUSINESS/steps
{
  "businessSteps": [
    { "stepName": "PAY_DUE_SAVINGS_CHARGES",   "order": 1 },
    { "stepName": "POST_INTEREST_FOR_SAVINGS", "order": 2 }
  ]
}
----

The update is validated per job by `ConfigJobParameterServiceImpl`; both failures answer `400 Bad Request` with the globalisation code `error.msg.invalid.request.body`:

* The list must contain at least one step (`A job needs to have 1 business step at least.`).
* Every step must be one of the savings steps. A step of another job, such as the Loan COB step `APPLY_CHARGE_TO_OVERDUE_LOANS`, is rejected with `[APPLY_CHARGE_TO_OVERDUE_LOANS] Business steps are not configurable for this job.`

=== Manager vs Worker mode

`SavingsCOBManagerConfiguration` is only active when `BatchManagerCondition` evaluates to true and `SavingsCOBWorkerConfiguration` only when `BatchWorkerCondition` does. In a single-node deployment both conditions are true and the same JVM does both roles; in a manager/worker deployment they activate on different nodes.

== Job Topology

The `savingsCOBJob` is composed of four sequential steps on the manager node:

[source]
----
savingsCOBJob (JobName.SAVINGS_COB)
  ├── Resolve custom job parameters - Savings Step
  ├── Savings COB partition - Step              (partitioner -> outboundRequests)
  ├── Stayed locked savings accounts - Step
  └── Unlock processed savings accounts - Step
----

Each worker partition runs the following flow (driven by `CobWorkerStepListener`):

[source]
----
savingsCOBWorkerStep
  ├── savingsInitialiseContext      (InitialisationTasklet — sets up FineractContext)
  ├── savingsApplyLock              (ApplySavingsLockTasklet — inserts locks)
  ├── chunk(SavingsAccount)         (reader -> processor -> writer)
  │     reader   : SavingsItemReader
  │     processor: SavingsItemProcessor      (runs the SavingsCOBBusinessStep chain)
  │     writer   : SavingsItemWriter         (saveAll + delete locks)
  └── savingsResetContext           (ResetContextTasklet)
----

The chunk step is fault tolerant: it retries up to `retry-limit` on any `Exception`, then skips, up to the skip limit (`skip-limit`, or `chunk-size + 1` when unset). `ChunkProcessingSavingsItemListener` intercepts `@OnReadError`, `@OnProcessError`, and `@OnWriteError` and records the failure against the per-account lock row in a `REQUIRES_NEW` transaction.

The manager step is built with a `COBStepExecutionSplitter` (`fineract-cob`). It persists the manager step's execution context, including the partition metadata, right after the partitioner runs and before any partition request is dispatched, so a restarted job reuses the original partition names instead of losing track of them if the manager dies while workers are still processing.

=== Partitioning logic

`SavingsCOBPartitioner.partition(int)` computes its partitions by paging through eligible account ids. The SQL is dialect-portable through `NamedParameterJdbcTemplate` and uses `row_number()` window-paging:

* Filter: `status_enum IN (SUBMITTED_AND_PENDING_APPROVAL, APPROVED, ACTIVE, TRANSFER_IN_PROGRESS, TRANSFER_ON_HOLD)`.
* When `isCatchUp = true`: only accounts where `last_closed_business_date = businessDate - 1`.
* When `isCatchUp = false`: accounts where `last_closed_business_date = businessDate - 1 OR last_closed_business_date IS NULL`.
* Output: a list of `COBPartition(min, max, page, count)` rows whose ids fall into the same `floor((rowNumber - 1) / partitionSize)` bucket.

If the configured business steps list is empty the partitioner calls `jobOperator.stop(jobId)` and returns no partitions. If there are no eligible accounts, a synthetic `(0, 0, 1, 0)` partition is emitted so the downstream worker step still runs cleanly.

=== Reader filter

`SavingsItemReader.beforeStep` re-runs `retrieveAllNonClosedSavingsByLastClosedBusinessDateAndMinAndMaxSavingsId` to get the savings ids within the partition's `[min, max]` range, then *retains only* those that actually have a `SAVINGS_COB_CHUNK_PROCESSING` lock placed for them by the `ApplySavingsLockTasklet`. This guarantees the chunk processor never touches an account that was not successfully locked first.

== Business Steps

Business steps are implementations of `SavingsCOBBusinessStep extends COBBusinessStep<SavingsAccount>`. They are Spring beans, discovered by `COBBusinessStepService`, and invoked in `step_order` for every `SavingsAccount` flowing through the chunk processor.

[source,java]
----
public interface SavingsCOBBusinessStep extends COBBusinessStep<SavingsAccount> {
    // String getEnumStyledName();   // matches m_batch_business_steps.step_name
    // String getHumanReadableName();
    // SavingsAccount execute(SavingsAccount input);
}
----

Six business steps ship with the feature, all enabled by default. They run in `step_order` for every account in the chunk:

[cols="1,1,1,3",options="header"]
|===
| Step name (`getEnumStyledName()`) | Human-readable name | Default order | Behaviour
| `POST_INTEREST_FOR_SAVINGS` | Post interest for savings | 1 | Posts interest for the account up to the current business date.
| `PAY_DUE_SAVINGS_CHARGES` | Pay due savings charges | 2 | Applies every active, unpaid, not-waived charge of an active account whose due date is on or before the business date.
| `APPLY_ANNUAL_FEE_FOR_SAVINGS` | Apply annual fee for savings | 3 | Applies active, not-fully-paid annual-fee charges whose due date is on or before the business date.
| `UPDATE_SAVINGS_DORMANT_STATUS` | Update savings dormant status | 4 | Advances the dormancy sub-status (NONE → INACTIVE → DORMANT → ESCHEAT) based on the product's inactivity thresholds.
| `UPDATE_DEPOSITS_ACCOUNT_MATURITY_DETAILS` | Update deposit accounts maturity details | 5 | Recomputes maturity details for fixed/recurring deposit accounts; plain savings deposits are skipped.
| `ADD_ACCRUAL_TRANSACTIONS_FOR_SAVINGS` | Add accrual transactions for savings | 6 | Adds the periodic accrual transactions of the account from its accrued-till date (or activation date) up to the business date.
|===

==== POST_INTEREST_FOR_SAVINGS

`PostInterestForSavingsBusinessStep` delegates to `SavingsAccountWritePlatformService.postInterest(account, false, businessDate, backdatedTxnsAllowedTill)`, where `backdatedTxnsAllowedTill` is read from `ConfigurationDomainService.retrievePivotDateConfig()`.

==== PAY_DUE_SAVINGS_CHARGES

`PayDueSavingsChargesBusinessStep` skips non-active accounts and, for each charge that is active, not fully paid, not waived, and due on or before the business date, calls `SavingsAccountWritePlatformService.applyChargeDue(chargeId, savingsId)`.

==== APPLY_ANNUAL_FEE_FOR_SAVINGS

`ApplyAnnualFeeForSavingsBusinessStep` skips non-active accounts (as the legacy job does) and, for each charge that is an annual fee, active, not fully paid, has a due date, and whose due date is not after the business date, calls `SavingsAccountWritePlatformService.applyAnnualFee(chargeId, savingsId)`.

==== UPDATE_SAVINGS_DORMANT_STATUS

`UpdateSavingsDormantStatusBusinessStep` asks `SavingsDormancyService.deriveDormancyTransition(account, businessDate)` for the next sub-status and applies it via the write service:

* `INACTIVE` → `setSubStatusInactive(savingsId)`
* `DORMANT` → `setSubStatusDormant(savingsId)`
* `ESCHEAT` → `escheat(savingsId)`

`SavingsDormancyServiceImpl` only acts on active accounts whose product has dormancy tracking enabled. It finds the date of the last customer activity with a single JPQL query, `SavingsAccountTransactionRepository.findLastTransactionDateBySavingsIdAndTypes`, which returns the maximum transaction date among the account's `DEPOSIT` and `WITHDRAWAL` transactions that are neither reversed nor reversal transactions (only customer-initiated activity resets the dormancy clock, as in the legacy `UPDATE_SAVINGS_DORMANT_ACCOUNTS` job). When there is no such transaction, or it is not after the activation date, the activation date is used instead. The service then measures the days from that date to the business date and compares that against the product's `daysToInactive`, `daysToDormancy` and `daysToEscheat` thresholds to derive the single next transition (or `null` when no transition applies).

==== UPDATE_DEPOSITS_ACCOUNT_MATURITY_DETAILS

`UpdateDepositMaturityDetailsBusinessStep` reads `savingsAccount.depositAccountType()` and, only when it is a deposit type other than `SAVINGS_DEPOSIT` (i.e. fixed or recurring deposits), calls `DepositAccountWritePlatformService.updateMaturityDetails(savingsId, depositAccountType)`. Plain savings deposits carry no maturity and are skipped.

==== ADD_ACCRUAL_TRANSACTIONS_FOR_SAVINGS

`AddAccrualForSavingsBusinessStep` (`fineract-provider`) calls `SavingsAccrualWritePlatformService.addAccrualEntries(savingsAccount, businessDate)`, where `businessDate` is `DateUtils.getBusinessLocalDate()`. A `MultiException` raised by the accrual service is rethrown as a `BusinessStepException` (same as Loan's `AddPeriodicAccrualEntriesBusinessStep`), so the failure goes through the chunk step's normal retry/skip handling and is recorded on the account's lock row.

== Locking

=== Lock ownership

Lock owners are values of the shared `org.apache.fineract.cob.domain.LockOwner` enum (the same enum that holds the loan owners). Savings COB uses two of them:

[cols="1,3",options="header"]
|===
| Value | Description
| `SAVINGS_COB_CHUNK_PROCESSING` | Held by the batch worker while a chunk is being processed
| `SAVINGS_INLINE_COB_PROCESSING` | Held by the inline catch-up job (`INLINE_SAVINGS_COB`) while it advances the requested accounts on demand
|===

`SavingsAccountLockServiceImpl.getCobLockOwners()` returns both values; every generic lock query of `AbstractAccountLockService` (hard-lock check, overrulable-lock check, orphaned-lock cleanup) is therefore scoped to the savings owners only.

=== Inline Savings COB

`InlineSavingsCOBExecutorServiceImpl` extends the shared `InlineCommonLockableCOBExecutorService`, so the inline Savings COB follows exactly the same rules as the inline Loan COB. It is exposed through the generic inline job endpoint (`InlineJobType.SAVINGS_COB` maps it to the `INLINE_SAVINGS_COB` Spring Batch job):

[source,json]
----
POST /jobs/SAVINGS_COB/inline
{
  "savingsIds": [1, 2, 3]
}
----

The `savingsIds` field is part of the OpenAPI contract: it is declared next to `loanIds` on the shared `InlineJobRequest` schema (`InlineJobResourceSwagger`), so the generated clients can send it. Through the Feign client the call is:

[source,java]
----
fineractClient.inlineJob().executeInlineJob("SAVINGS_COB", new InlineJobRequest().savingsIds(List.of(1L, 2L, 3L)));
----

* *Request size limit:* the number of ids is limited by `fineract.api.body-item-size-limit.inline-loan-cob` (the same property as the loan inline COB, 1000 by default). A larger list is rejected with `PlatformRequestBodyItemLimitValidationException`, which answers `400 Bad Request` with the globalisation code `error.msg.validation.request.body.item.limit.validation` and the message `Size of the savings IDs list cannot be over N`.
* *Accounts processed:* only the requested accounts that are behind the COB date (or were never closed) are processed. The job runs once per business date, from the day after the oldest `last_closed_business_date` up to the COB date, and each run only includes the accounts still behind that date.
* *Lock takeover:* before each run the executor takes the locks in a `REQUIRES_NEW` transaction under `SAVINGS_INLINE_COB_PROCESSING`. A lock held by another COB run *without* an error cannot be overruled and the request fails with `AccountLockCannotBeOverruledException`, unless the authenticated user is the bypass user. A lock *with* an error is taken over, and its previous error and stacktrace are cleared so a later failure is not reported under the old one.
* *Retry:* each business date is retried as a whole attempt, lock takeover included, according to `fineract.retry.instances.inlineCob.*` (`max-attempts`, `wait-duration`, `enable-exponential-backoff`, `exponential-backoff-multiplier`).
* *Failure recording:* a failed attempt records its error and stacktrace on the locks it placed (only those whose version has not changed since and that carry no error yet), which makes them overrulable for the next attempt or a later request. A job execution that did not complete surfaces as `error.msg.sheduler.job.execution.failed`.
* *Chunk errors:* errors raised while reading, processing or writing an account inside the inline job are recorded on its lock row by `InlineCOBSavingsItemListener` under `SAVINGS_INLINE_COB_PROCESSING`.

NOTE: Unlike Loan COB, there is currently no servlet filter (no Savings equivalent of `LoanCOBApiFilter` or `WorkingCapitalLoanCOBApiFilter`) that auto-triggers a catch-up COB when a write API is called against a savings account that is behind on COB. The inline Savings COB only runs when it is invoked explicitly through the endpoint above.

=== Lock lifecycle

. `ApplySavingsLockTasklet` (which extends the generic `ApplyCommonLockTasklet`) selects all eligible ids in the partition, removes those already locked (so it never re-locks), and bulk-inserts `SAVINGS_COB_CHUNK_PROCESSING` rows into `m_savings_account_locks` via `SavingsLockingServiceImpl.applyLock(...)`. The insert runs in a `PROPAGATION_REQUIRES_NEW` transaction. On failure the tasklet counts the attempt in the step execution context and returns `CONTINUABLE`; after more than 3 failed attempts it raises `LockCannotBeAppliedException`.
. The chunk reader filters its working set down to ids that actually have a `SAVINGS_COB_CHUNK_PROCESSING` lock.
. The processor runs the business-step chain and sets `lastClosedBusinessDate = businessDate` on the account.
. The writer persists the chunk via `RepositoryItemWriter` and then calls `LockingService.deleteByLoanIdInAndLockOwner(ids, SAVINGS_COB_CHUNK_PROCESSING)` in the same transaction (the generic method name is kept; for savings the ids are savings account ids).
. If any read/process/write error occurs, `ChunkProcessingSavingsItemListener` writes the error message and stacktrace to the lock row and the lock is *kept*.
. The `StayedLockedSavingsTasklet` at the end of the job calls `findAllStayedLockedByCobBusinessDate(cobBusinessDate)` and, if any rows come back, publishes a `SavingsAccountsStayedLockedBusinessEvent`.
. The `UnlockProcessedSavingsTasklet` calls `AccountLockService.removeOrphanedLocksForProcessedAccounts()`, backed by `SavingsAccountLockRepository.deleteOrphanedLocksForProcessedAccounts`. It deletes any `SAVINGS_COB_CHUNK_PROCESSING` or `SAVINGS_INLINE_COB_PROCESSING` lock row whose `error` is `null` and whose account's `last_closed_business_date` already equals the lock's `lock_placed_on_cob_business_date` (i.e. processing actually finished but the lock delete didn't land).

=== Locking SQL

`SavingsLockingServiceImpl` uses two JDBC batch statements:

[source,sql]
----
-- applyLock
INSERT INTO m_savings_account_locks
  (savings_id, version, lock_owner, lock_placed_on, lock_placed_on_cob_business_date)
VALUES (?, ?, ?, ?, ?);

-- upgradeLock
UPDATE m_savings_account_locks
SET version = version + 1, lock_owner = ?, lock_placed_on = ?
WHERE savings_id = ?;
----

Both are batched in slices of `fineract.query.in-clause-parameter-size-limit` rows.

== Business Events

=== Overview

The COB job emits one business event when accounts could not be unlocked at the end of the run.

=== SavingsAccountsStayedLockedBusinessEvent

*Category:* `Savings COB`

*Type:* `SavingsAccountsStayedLockedBusinessEvent`

Emitted by `StayedLockedSavingsTasklet` at the end of `savingsCOBJob` whenever
`findAllStayedLockedByCobBusinessDate(cobBusinessDate)` returns a non-empty list. The payload `SavingsAccountsStayedLockedData` contains a list of `COBIdAndExternalIdAndAccountNo(id, externalId, accountNo)` for every savings account whose lock row remained associated with the current COB business date.

The event is registered in `m_external_event_configuration` (migration `2004_add_savings_account_cob_infrastructure.xml`) with `enabled = false` by default — operators turn it on per tenant to receive externalized notifications.

== Validation Rules

The batch job has no user-facing input and therefore no API-level validation. The user inputs are the inline request body, whose `savingsIds` list is limited by `fineract.api.body-item-size-limit.inline-loan-cob` (see <<Inline Savings COB>>), and the business step list, which must be non-empty and contain only savings steps (see <<savings-cob-business-step-configuration,Business step configuration>>). Internal invariants enforced by the pipeline:

* The partitioner refuses to dispatch any partition when no `SavingsCOBBusinessStep` is configured for `SAVINGS_CLOSE_OF_BUSINESS` in `m_batch_business_steps`; it stops the job execution.
* The reader filters out any partition member that does not currently hold a `SAVINGS_COB_CHUNK_PROCESSING` lock.
* `ApplySavingsLockTasklet` retries lock acquisition up to 3 times (the attempt counter lives in the step execution context); beyond that it raises `LockCannotBeAppliedException`.

== Business Rules

=== Account selection

* Only savings accounts in `SUBMITTED_AND_PENDING_APPROVAL`, `APPROVED`, `ACTIVE`, `TRANSFER_IN_PROGRESS`, or `TRANSFER_ON_HOLD` are eligible.
* Accounts whose `last_closed_business_date` is already at or beyond `cobBusinessDate - NUMBER_OF_DAYS_BEHIND` (i.e. already processed for that date) are skipped.
* `NUMBER_OF_DAYS_BEHIND` is inherited from `COBConstant.NUMBER_OF_DAYS_BEHIND = 1L`.

=== Catch-up mode

* When the job parameter `IS_CATCH_UP = true`, the partitioner and reader only consider accounts where `last_closed_business_date = cobBusinessDate - 1`. This is the entry point used to re-process accounts whose previous COB run left them in a stayed-locked state, after manual intervention has cleared the lock.

=== Idempotence

* The processor sets `lastClosedBusinessDate` to the current business date as the last action of `process(...)`. A re-run for the same business date will therefore skip already-advanced accounts at partition selection time.
* Business steps are expected to be idempotent within a single business date; a chunk-level retry will re-invoke `execute(...)` for the same account.

== Example Scenarios

=== Scenario #1: Nightly COB advances a healthy tenant

*Setup:*

* `m_batch_business_steps` for `SAVINGS_CLOSE_OF_BUSINESS` contains the six seeded steps (`POST_INTEREST_FOR_SAVINGS`, `PAY_DUE_SAVINGS_CHARGES`, `APPLY_ANNUAL_FEE_FOR_SAVINGS`, `UPDATE_SAVINGS_DORMANT_STATUS`, `UPDATE_DEPOSITS_ACCOUNT_MATURITY_DETAILS`, `ADD_ACCRUAL_TRANSACTIONS_FOR_SAVINGS`).
* The `Savings COB` job has been activated and the legacy standalone savings jobs deactivated (see <<Upgrade and coexistence with the legacy savings jobs>>).
* `BusinessDate` is 2026-06-09; all eligible savings accounts have `last_closed_business_date = 2026-06-08` or `NULL`.
* `partition-size = 100`, `chunk-size = 100`.

*Action:*

The `Savings COB` scheduled job fires. The manager partitions accounts into id-range buckets of 100 and pushes them onto `outboundRequests`. Workers pull each partition, place locks, run the six business steps in order against each account, persist, release locks.

*Expected Behavior:*

* Every eligible account has `last_closed_business_date` advanced to 2026-06-09.
* `m_savings_account_locks` is empty at the end of the run.
* `StayedLockedSavingsTasklet` finds no rows and emits no event.
* `UnlockProcessedSavingsTasklet` deletes 0 rows.

=== Scenario #2: A single account fails interest posting

*Setup:*

* Same configuration as Scenario #1.
* Account `12345` is in an inconsistent state that makes `postInterest` throw a `RuntimeException` every time, including on retry.

*Action:*

The chunk-step retries `12345` up to `retryLimit` times, then skips it. `ChunkProcessingSavingsItemListener.onProcessError` writes `"Savings (id: 12345) processing is failed"` and the serialized stacktrace to the row in `m_savings_account_locks` for that account.

*Expected Behavior:*

* All accounts other than `12345` advance and have their locks released.
* The lock row for `12345` remains, with `error` and `stacktrace` populated.
* `StayedLockedSavingsTasklet` finds `12345` and publishes a `SavingsAccountsStayedLockedBusinessEvent` containing `(12345, externalId, accountNo)`.
* `UnlockProcessedSavingsTasklet` does *not* delete `12345` because its `error` column is non-null.
* On the next day's run, `12345` is excluded from partitioning (its `last_closed_business_date` is now more than one day behind) and its lock row stays in place. It can be advanced again after operator review, for example with an inline COB request (`POST /jobs/SAVINGS_COB/inline` with `"savingsIds": [12345]`), which is allowed to take the lock over because the lock carries an error.

== Upgrade and coexistence with the legacy savings jobs

*What is new:* the `Savings COB` job (`JobName.SAVINGS_COB`) runs the daily savings processing — interest posting, due charges, annual fees, dormancy, deposit maturity and accruals — as one partitioned, per-account-locked batch job, plus an inline variant (`POST /jobs/SAVINGS_COB/inline`) to bring selected accounts up to date on demand. *What operators must do:* nothing on upgrade; to switch over, activate the `Savings COB` job and deactivate the legacy savings jobs listed below in the same change.

The `Savings COB` row in the `job` table is seeded with `is_active = false` by `2007_add_savings_cob_job_data.xml`, so upgrading changes nothing for existing tenants: the job does not run until an operator activates it. The legacy standalone savings jobs are still defined in `JobName` (each with its own Spring Batch configuration under `org.apache.fineract.portfolio.savings.jobs`) and keep doing the same work they did before.

Each default Savings COB business step performs the work of one legacy job:

[cols="2,2,2",options="header"]
|===
| Legacy job (`JobName`) | Display name | Savings COB business step
| `POST_INTEREST_FOR_SAVINGS` | Post Interest For Savings | `POST_INTEREST_FOR_SAVINGS`
| `PAY_DUE_SAVINGS_CHARGES` | Pay Due Savings Charges | `PAY_DUE_SAVINGS_CHARGES`
| `APPLY_ANNUAL_FEE_FOR_SAVINGS` | Apply Annual Fee For Savings | `APPLY_ANNUAL_FEE_FOR_SAVINGS`
| `UPDATE_SAVINGS_DORMANT_ACCOUNTS` | Update Savings Dormant Accounts | `UPDATE_SAVINGS_DORMANT_STATUS`
| `UPDATE_DEPOSITS_ACCOUNT_MATURITY_DETAILS` | Update Deposit Accounts Maturity details | `UPDATE_DEPOSITS_ACCOUNT_MATURITY_DETAILS`
| `ADD_PERIODIC_ACCRUAL_ENTRIES_FOR_SAVINGS_WITH_INCOME_POSTED_AS_TRANSACTIONS` | Add Accrual Transactions For Savings | `ADD_ACCRUAL_TRANSACTIONS_FOR_SAVINGS`
|===

[IMPORTANT]
====
When activating `Savings COB`, deactivate every legacy job in the table above that is active for the tenant. Nothing prevents both from running: if a legacy job stays active, the same work (interest posting, charges, fees, dormancy, maturity, accruals) is scheduled twice a day for the same accounts, once by the legacy job and once by the COB step. Conversely, removing a step from `m_batch_business_steps` for `SAVINGS_CLOSE_OF_BUSINESS` hands that work back to its legacy job, which must then stay active.
====

== Summary

Savings COB ports the proven LoanCOB partitioned-batch architecture to savings accounts, providing a configurable, fault-tolerant, horizontally scalable end-of-day pipeline. Key aspects:

* Manager/worker Spring Batch topology with `RemotePartitioningManagerStepBuilderFactory` and `RemotePartitioningWorkerStepBuilderFactory`, activated through `BatchManagerCondition` / `BatchWorkerCondition`.
* Per-account distributed lock in `m_savings_account_locks`, built on the generic `AccountLock` / `AccountLockRepository` / `AbstractAccountLockService` contracts, with two `LockOwner` values (chunk processing and inline) and explicit stayed-lock and orphaned-lock cleanup steps.
* Inline Savings COB (`POST /jobs/SAVINGS_COB/inline`) sharing the lock-takeover, retry and failure-recording rules of the inline Loan COB.
* Extensible pipeline through the `SavingsCOBBusinessStep` interface and the tenant-scoped `m_batch_business_steps` table, shipping with six steps enabled by default: interest posting, due-charge payment, annual-fee application, dormancy-status update, deposit-maturity update and accrual posting.
* Scaling through partitioning (smaller `partition-size`, more worker instances); the worker step has no task executor by design.
* Seeded inactive, so the legacy standalone savings jobs keep working until an operator switches over.
* Catch-up mode that targets only accounts whose previous COB run did not complete, enabling safe re-processing.
* Business-event `SavingsAccountsStayedLockedBusinessEvent` that surfaces every account left locked at end-of-run, so downstream tooling can alert or auto-remediate.
